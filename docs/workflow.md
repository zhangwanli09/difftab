## 9. 开发方式

**文档体系的形态：`docs/` 一节一文件，索引在 [`docs/README.md`](README.md)。** 需求与设计的唯一事实来源是 `docs/` 目录整体（不是其中某一份），已收口阶段的记录是 `docs/journal.md`，常驻上下文是根目录的 `CLAUDE.md`。拆成多文件的理由与本节下方 `CLAUDE.md` 预算条是同一条：**被路由的那一端也得能按需加载**——路由表把“改这块 → 读哪节”指清楚了，而读取的最小单位在工具层面是文件，章节级的指路仍要付整份文档的上下文。角色划分照搬业界 spec-driven development 的通行切法（常驻宪法 / 需求 / 设计 / 验收 / 阶段 / 决策依据各自成文），**但不引入其配套工具链与 per-feature 目录形态**——本项目是单产品加大量横切不变量（只读性、红线），按特性分目录只会让同一条约束被复制多份。

- **§ 号是外部稳定地址：可以搬文件，不可以重新编号。** `spec §5.x` 这类引用不只在文档之间，还散落在 `biome.json`、三份 tsconfig、`vite.config.ts`、`tsdown.config.ts`、`vitest.config.ts`、`lefthook.yml` 与 `test/smoke/*.js` 里共约 30 处。**重新编号不会报错**——lint、类型检查、测试、门禁全都不读注释，唯一的症状是若干条“依据见 §5.x”从此指向一段不相干的内容，而那恰恰是改动 git 调用或监听逻辑时最需要它指对的时刻。因此拆分、合并、移动文件都允许，前提是章节号原样跟着走；`docs/README.md` 的映射表负责把号解析成文件。
- **中文标点按 GB/T 15834-2011 用全角**（2026-08-23 统一）：`，；：（）` 与引号 `“”` 一律全角，`。、「」——……` 本就是全角。三类**不**转：数字千分位（`1,048,945`）、成段英文引文的内部（`"…summaries, statistics, and changelogs"`）、代码块与行内代码里的一切。破折号 `——` 占两个字位、**前后不加空格**。另有一条不属于标点却同源：**段落不要在两个汉字之间硬换行**——markdown 会把那个换行渲染成一个可见空格，源码里看不出来，只有在网页上才看得见（`README.zh-CN.md` 的接缝因此只落在拉丁文与代码那侧）。**这条没有门禁**，改文档时靠自觉；它坏掉的样子就是本文件反复说的那种——不报错，只是难看。
- **新增内容前先判断落哪个文件，别就近塞。** 判据与拆分前一致：规则与理由进 `design.md` §5，实测输出与被排除的做法进 `decisions.md` §10，可勾的判据进 `acceptance.md` §6，阶段安排进 `roadmap.md` §7——两处不互相复述。新增或移动文件时，同步 `docs/README.md` 的映射表与 `CLAUDE.md` 的两张路由表。

- 全程使用 Claude Code 进行开发，按 `roadmap.md` §7 S0–S6 顺序推进
- 项目根目录维护 `CLAUDE.md`，避免开发过程中“发明”未授权的写操作或功能。**`CLAUDE.md` 是每轮会话无条件加载的常驻上下文，因此只承载摘要与路由，不承载论证**——**至少**包含以下三部分：
  - `spec.md` §4 Non-goals **摘要**（4.1、4.2 两类各保留条目本身，理由删去）
  - `decisions.md` §10 「被排除的做法」中**违反后不报错、只是静默出错**的条目，压成一行式红线。**切割线是「留后果、删证据」**：某条违反后会静默地坏成什么样，是识别情境的触发器，必须留在 `CLAUDE.md`；实测数字、run id、推导过程、“已实测”之类的背书一律留 `decisions.md` §10。**一条规则占一行**（理由见下方预算条）
  - 一张「改哪块 → 动手前先读 `docs/` 哪个文件的哪节」的路由表，**覆盖 `design.md` §5 各小节**（5.0–5.12 每节都要有落点）

  另按实际需要承载几项同样“每轮都用得上、且不适合放进 `docs/`”的内容，当前为：产品定位一句话、**两个 git 作用域的区分**（产品运行时的 git 受零写操作约束，开发流程的 git 不受——这条不澄清会导致工具拒绝执行本仓库的正常版本控制操作）、提交约定、常用命令表、**发布与维护约定**（S6 之前这一格是「开发阶段概览」，已按本节末条退场，见下）。新增此类内容前先确认它不属于“论证”，论证一律留在 `docs/` 的对应文件。

  **曾经还有一张「做哪个阶段 → 本会话必读哪几节」的表，已随文档拆分一并删去。** 它唯一要解决的问题是需求文档整篇 47k token 读进来会挤掉实现所需上下文，而拆成一节一文件之后，每份都能单独打开（最大的 `design.md` 约 21k、`roadmap.md` 约 3.5k），上面那张「改这块 → 读哪份的哪节」的路由表已经把切口给足了。**判据留在此处以免它被重新提出**：凡是当初只因为“打开事实来源太贵”才复制进 `CLAUDE.md` 的东西，拆分之后都要重新过一遍这条问句——推导不出来的、或要扛 `/compact` 的才留，单纯图省事的副本一律删。

  **「开发阶段概览」曾只承载两样：当前进度、尚未消费的跨阶段交接**；S6 收口时它按本节末条整体退场，判据留在此处以免被重新提出。阶段序列本身在 `roadmap.md` §7 有全表，`CLAUDE.md` 当时只给一句指路；收口后的实测数字与踩坑记录写 `docs/journal.md`，同样不留副本。留下那两样各有非留不可的理由：**当前进度推导不出来**（要读 §6 的勾选或翻 journal 才知道停在哪），**未消费的交接以那一节为唯一来源**且正是会被 `/compact` 冲掉、而下一个阶段又必须看见的那类。理由是**只有这部分按阶段线性增长**——每收口一次就多一段，而 `CLAUDE.md` 每轮无条件全量加载，不给它定去处就会把红线和路由挤在一份越来越贵的常驻上下文里（增长实况随时可由 `git log -- CLAUDE.md` 重算，不在此复制）。**阶段推进结束后这两条理由同时失效**：没有下一个阶段，也就没有“当前进度”和“未消费的交接”——所以退场不是清理，是那一节的读者没有了。
- **`CLAUDE.md` 的预算是 ≤ 200 行，且一条规则占一行**。200 行取自 Claude Code 官方 memory 文档的建议（*“target under 200 lines per CLAUDE.md file”* / *“Longer files consume more context and reduce adherence”*）。**两半必须同时成立，缺一则度量失效**：行数能被“把十几条规则塞进一个 bullet”轻易做低，那样的文件行数好看而实际不可扫读，恰好撞上官方另一条判据（*“organized sections are easier to follow than dense paragraphs”*）。**禁止再给它补字节 / KB 上限**——中文 UTF-8 3 字节/字，字节维度远早于行数触顶，一旦并设，真正生效的约束就只剩字节，而省字节最省事的手段恰恰是把多条规则挤进一行长句，等于奖励上一句刚禁掉的写法。

  **超出预算时先问“这段能不能下沉到 `docs/` 的对应文件或 `docs/journal.md`”，而不是接着往下写**；红线（`decisions.md` §10 的静默出错条目）与路由表**不参与裁剪**——它们正是官方裁剪判据里要保留的那一类（pitfalls 与“与工具默认不同的约定”），而可裁的是能从代码库、git log 或本文档推导出来的内容。**也不要把红线下沉到 `.claude/rules/` 的 path-scoped 规则**：官方文档写明「项目根的 `CLAUDE.md` 在 `/compact` 后会被从磁盘重读并重新注入，子目录的 `CLAUDE.md` 与带 `paths:` 的规则不会自动重注入」，而红线要防的恰是**上下文被压缩之后、新建文件时就踩**的那一类——`roadmap.md` §7 论证过的“红线条目能活下来”依赖的正是根文件这条重注入路径
- **`decisions.md` §10 仍是「被排除的做法」的唯一来源**，`CLAUDE.md` 不再逐条转写整表；增删禁止项只改 `decisions.md` §10，避免同一条约束散落多处、改一漏二。同理，**`docs/journal.md` 是已收口阶段记录的唯一来源**——它是记录不是约束，任何一条在其中沉淀出的通用规则，要么进 `decisions.md` §10、要么进 `CLAUDE.md` 红线，不靠读日志来生效
- 每个阶段完成后，对照 `acceptance.md` §6 中标记为本阶段的验收项自查，不堆到后期集中验证
- **`CLAUDE.md` 的「开发阶段」一节已于 S6 整体退场，换成「发布与维护约定」**（2026-08-19 执行）。阶段推进到此结束，再留一句“S6 已收口”就没有读者了——而常驻上下文里的僵尸条目不会有人主动想起来删，所以退场条件当初写在这里，和阶段本身一起收口。**接替它的那一节承载的是另一类东西**（发布步骤的去处、semver 口径、两份 README 要同步），判据同上：每轮都用得上、且推导不出来

**阶段收口判据（Definition of Done）**——一个阶段算完成，须同时满足四条：

1. `acceptance.md` §6 中标记为本阶段的验收项**全部**打勾；因客观条件（如缺真机）无法当场验证的，显式记为待 S5 复核，而不是默认通过
2. `biome ci`、`tsc --noEmit`、`pnpm test`，以及截至本阶段已建立的冒烟与门禁脚本（只读性两层验证、体积、冷启动）全部为绿
3. `CLAUDE.md` 第 3 节命令表已补全本阶段新增的 `package.json` script，`CONTRIBUTING.md` 的 Gates 表同步核对过（S6 起对外多了这一份，而它是唯一一份给外部贡献者看的）
4. 本阶段的收口记录与踩坑写入 `docs/journal.md`（倒序追加一节），`CLAUDE.md` 第 7 节**只**更新当前进度与未消费的交接条、并删去已被本阶段消费的交接；收口前核对 `CLAUDE.md` 仍在 200 行预算内、且新增红线是一条一行。**第 7 节这半条随 S0–S6 一并结束**（该节已按上一条退场），此后仍成立的是前一半与 200 行预算
