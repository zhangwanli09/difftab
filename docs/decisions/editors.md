# 右侧面板：标签页、分屏与正文视图

> 收录规则与实测环境见 [`README.md`](README.md)。其余前端决策见 [`web.md`](web.md)。

- **`position: sticky` 的滑动余量来自包含块，不是滚动容器**（Chrome 实测）：文件视图的行号槽 `sticky left-0` 长期不生效，因为它的包含块只有面板那么宽（960px），而横向滚动发生在外面那个 `<section>` 上、内容实测宽 9446px——**余量为 0 时 sticky 与 static 在页面上完全一样**，没有任何东西会响。给那一层 `w-max` 之后包含块与内容齐宽，行号槽的 `left` 实测从 -266 回到 320（= 面板左缘）。**代价是这个类只能给正文那一路**：`max-content` 下 `break-all` 不再起作用（它只降 min-content），一条 60 层的相对路径实测把提示行撑到 **1977px**、而面板 960px——去掉 `w-max` 后同一条回到 960px 正常折行。
- **`<img src>` 字串不变时 Preact 不改属性、浏览器不重新请求**：SSE 刷新后 `loadDiff` 落进来的是新 payload 对象，两侧 `path` / `side` 一字不变——`v=` 不随内容变时右图停在旧的那张，控制台一条都不报。第一版把 `v=` 做成 `useMemo(() => Date.now(), [payload])`，图确实换了，代价是每一次无关文件的 SSE（`refresh()` 对活动 tab 无条件重取）都重挂两张图、重下最多 10MB 外加一次 `cat-file blob`，且依赖「`getJson` 永远给新对象、缓存永不去重」这条没写下来的契约。现在 `v=` 是后端给的内容身份（`ImageSide.version`）。
- **图片视图的棋盘复用 `--color-diff-diagonal-fill`**：那个 token 本就是「叠在编辑器底色上、明暗两档都成立」的 6% 半透明，`repeating-conic-gradient` 两格交替即成棋盘，不为它新开颜色（`@theme` 里没人引用的 token 会被裁，多开一个就多一处要被 `check:css` 看着的地方）。

## 被排除的做法

| 做法 | 排除原因 |
|---|---|
| 右侧标题栏用滚动容器内的 `sticky top-0` 钉住 | 要靠 `z-10` 与实心底色去躲补丁里那些定位过的行号格（当时是 diff2html 的 `position:absolute`，后来是 `sticky`，都排在横杠之后）；文件视图那侧还得靠外层 `w-max min-w-full` 与一个 `sticky left-0` 的 span 才铺得满、留得住，`px-4` 与 `left-4` 两个数字从此绑死。把横杠排到滚动容器之外，这几处一起消失——越界的盒子被容器的 `overflow` 裁掉，够不着它 |
| 文件内容构造成「全新增 diff」交给 diff 视图渲染 | 省下一个渲染路径，代价是每一行前面都挂着 `+`、整片底色是新增绿——读起来像在审一份补丁而不是读一个文件，而「看项目整体面貌」正是要摆脱补丁视角。被否的是整片底色与 `+`：行号旁 3px 宽的改动标记（VS Code quick diff）不把文件读成补丁，不在此列 |
| Markdown 渲染用 markdown-it 或 micromark + 插件 | markdown-it 压缩后约 100 KB，是 marked 的两倍多；micromark 要 GFM 得再装四五个扩展包，每个都是一份要跟着升级的依赖。`marked` 零运行时依赖、同步 API、GFM 内建，且 renderer 按 token 覆盖（代码块的 hljs 高亮就是覆盖一个方法）。实测（`marked@18.1.1`）产物 JS 249.5 → 297.9 KB 明文、86.1 → 101.4 KB gzip（含白名单清洗），CSS +2.4 KB 明文 / +0.5 KB gzip；gzip 那道门禁余量从 34 KB 缩到 18.6 KB，再加库之前先看这一行 |
| Markdown 里的原始 HTML 一律按文本转义（第一版的做法） | 在本仓库自己的 README 上实测：顶上居中的 logo、徽章与 `<picture>` 截图成了一大段标签源码，正是最常被打开的那个文件最难看。改成白名单清洗 |
| 原始 HTML 交给 DOMPurify 清洗，或只靠 CSP 兜底 | DOMPurify 又是一份约 20 KB 的依赖，而要的只是一张标签表、一张属性表与链接 / 图片两条规则，浏览器自带的 `<template>` 就是惰性的解析器；只靠 CSP 时脚本是拦住了，可一句 `class="fixed inset-0"`（Tailwind 工具类都在产物里）照样能把整张页面盖掉 |
| Markdown 预览与 SVG 预览共用一个开关 | 两者的默认相反：SVG 的文本几乎没人读，默认看图；`.md` 的源码本身可读，照 VS Code 默认看源码。共用一个 signal 时总有一边的默认是错的，而按钮本就只有一枚（一个文件不会两者都带），分开只多一个 signal |
| Markdown 的 diff tab 也能切渲染（两版并排，照 SVG） | 两份渲染结果并排看不出改了哪一行，读 diff 正是为了这个；VS Code 的 diff 编辑器也没有这一档。真要看改后的样子，开同一路径的 file tab 即可 |
| 后台 tab 用一个 stale 标记记「SSE 后没重取」，激活时按标记决定取不取 | 多一份要在收编、改名、关闭各处维护的状态，而它省下的只是「切过去时内容没变也发一趟」那一次请求。`activateEditor` 每次都真的去取，与目录树的 `loadDir` 同一取向 |
| 关掉活动 tab 后按最近使用顺序（MRU）选下一个 | 要多维护一份访问序列，换来的只是关掉一个刚从别处切过来的 tab 时少切一次。右邻居优先、否则左邻居，一眼能预期 |
| 编辑器 tab 上常显整段目录（上一版的做法） | 每个 tab 都宽出一截，而栏里多数时候没有同名文件、目录什么也没区分；VS Code 的默认 `labelFormat` 也只在撞名时才补 |
| 撞名时画整段目录 | 能区分的那段常在中间（`packages/foo/src` 与 `packages/bar/src`），而目录排在名字后面、`max-w-64` 从右端裁，两个 tab 裁完还是一个样 |
| 撞名时照搬 VS Code `labels.ts` 的 `shorten` | 找的是最短的唯一**连续**段，结果是 `…/foo/…` 这种两头都省的形式，读的人得自己补出它在路径里的位置；移植下来约 80 行。取尾段的公式一行能说清，产出的总是一段完整的路径后缀 |
| commit tab 的名字也按工作区状态染色 | 那份补丁是历史，工作区的 `M` 说的是另一份内容；同一个文件在两次提交里的 tab 会被染成同一个颜色，而它们与工作区的关系各不相同 |
| 编辑器标签栏用 `overflow-x-hidden` 去掉滚动条 | `scrollIntoView` 照样能把活动 tab 滚进来，但用户自己滚不了——溢出之后前面的 tab 只能靠关掉后面的才够得着。`scrollbar-width: none` 只是不画滚动条，滚动能力一样不少 |
| 编辑器标签栏的分隔线写成外层的 `border-b`、tab 留 `-mb-px` | 外层如今为了右端的动作区本就存在，但 tab 住在 tablist 这个滚动容器里，压出去的那 1px 照样被它裁掉。外层画一条 inset 阴影当分隔线，tab 的 `border-b` 落在它最后 1px 上盖过它（`divider-b`） |
| `Copy file contents` 浮在全文正文的右上角（GitHub 代码块那种） | 正文那层是双向滚动容器、内容 `w-max`，浮层要在两个轴上都 sticky 才留得住，且会盖住长行末尾的代码。标签栏本就在滚动区之外，右端放动作照 VS Code editor title 的 actions |
| 分隔线写成内联的 `shadow-[inset_0_-1px_var(--color-panel-border)]` | Tailwind 的 `shadow-*` 会把整套 shadow / ring 变量机制拖进产物：实测 CSS +2.2 KB（14 条 `@property` 注册、`@layer properties` 兜底块翻倍、五段式 `box-shadow` 里四段是 `0 0 #0000` 空转），为一条 1px 分隔线付整套机制；一条 `@utility divider-b { box-shadow: … }` 是 200 字节，测试也能钉一个名字而不是一段任意值的拼写 |
| 图片视图做缩放、滑块、洋葱皮、像素 diff | 图片视图只回答「改成了什么样」，新旧并排已够；那几样各要一段交互状态，而它们对「瞥一眼」没有增量 |
| 右侧空态照 VS Code 在快捷键列表上方画一枚大号 logo 水印（单色、压进底色的 letterpress） | 做出来看过，在这个面板里显得突兀：VS Code 的水印是填满整片编辑区的品牌符号，而 difftab 的符号是三条横条，放大到 256px 读起来像一块加载中的骨架屏，不像一枚标识。快捷键列表单独成立，不靠它撑 |
| SVG 直接进图片表、只画成图 | agent 改 SVG 多半是改几个坐标或颜色，文本 diff 说得出「改了哪一行」，两张图并排说不出；反过来只看文本又看不出长什么样。于是两样都留、预览是一枚开关；**默认开**：打开一个 SVG 先想知道它长什么样，要追「改了哪一行」再关掉，关了在本页面内一直关着。也不在 diff 上方常驻一行缩略图：大 SVG 会把补丁挤下去 |
| 图片 tab 做成第三种 `EditorKind` | tab 的身份是「视图种类 + 路径」，图片不是新的视图种类，只是 diff / 全文两种视图的正文换成了图；加一种要连累 `EditorTabs` 图标、`cacheOf`、`refresh` 三处 |
| 跳到行时把 hljs 输出按行切开、给每行一个元素 | 行高固定（`leading-5`）时按行号乘行高就能定位，高亮带是一个绝对定位的兄弟元素，不必为跳行付一行一个元素的 DOM；切也只能用 diff2html 现成的 `closeTags`，自己重写切分是被禁止的。**自动换行开着时例外**：行高不再固定，那一档用 `closeTags` 切行 |
| 自动换行时仍保留两个 `<pre>`，逐行量出位置（`Range.getClientRects`）再画行号 | 5 万行就是 5 万次排版查询，面板宽度一变（拖侧栏、分屏把手、窗口）都要重量一遍，量完之前行号是错的；空行与跨 span 的行首还各要一套取矩形的特例。切成行之后行号由同一行撑高，排版引擎自己对齐，不必量 |
| 整次提交视图一次取全部文件的补丁（或给后端加一个端点、一次回整次提交的补丁） | 一个提交改几百个文件时就是几百趟 `git diff` 或一份几十 MB 的响应，而用户多半只看前几段；新端点还要再进只读门禁与冒烟一遍。按视口懒取复用现成的 `/api/commit-diff`，取的量跟着滚动走 |
| 整次提交视图的上下文档挂在 tab 上一份（同 commit tab） | 点开一段的折叠行后，同一个 tab 里此后每取一段都按整份上下文取——几百段里只有用户点过的那一段需要它，其余每段都多拉一份整文件。按段记，代价只是 store 里多一张按段键的表、随整组 `forget` 清掉 |
| 工作区改动视图按分组各开一个（`Staged Changes` 一个、`Changes` 一个） | diff 的基准是 `git diff HEAD`，同一个文件在两组里是同一份补丁，分组开只是把同一份内容排两遍；本工具不做 stage，分组在这里是读状态用的 git 语义，不是两份可以分别查看的内容 |
| 工作区改动视图每次 SSE 重取全部段（或全部取到过的段） | agent 跑动期间事件密集，改几百个文件时每个事件就是几百趟 `git diff`，而屏幕上只有三四段；看不见的段记下「对着第几份 state 取的」，进入视口时再判，取的量跟着视口走 |
| 改动全清空时自动关掉工作区改动 tab（同 diff tab 收编） | diff tab 关掉是因为它说的那一行改动已不存在；这个 tab 说的是「工作区」，工作区一直在。agent 提交一次就关，用户正盯着的 tab 会在下一批改动到来之前消失，下一批来了还得再去点一次 |
| 工作区改动视图的段与 diff tab 共用 `diffCache` | 两边取的时机与上下文档的归属都不同：diff tab 每次 SSE 由 `refresh` 重取、档位挂在 tab 上，段由可见性驱动、档位按段记。共用一格时两边按各自那档轮流改写，点开一边的折叠行另一边的表格跟着换；省下的只是同一个文件两处都开着时的一趟请求 |
| 分屏做成 VS Code 那种任意嵌套的网格，或允许上下分 | 「同时看两份」两组左右并排就答完了；网格要一棵分割树、每个节点一把把手、四个方向的投放区，状态与拖放判定都多一个数量级，换来的是一个只读 diff 工具里很少有人摆得出的布局。diff 本来就宽，上下分时每组只剩半屏高 |
| 分屏的拖放用 pointer 事件自绘（同 `Sash`） | 要自己画跟着指针走的拖影、自己做命中测试、自己处理指针离开窗口；HTML5 drag and drop 这些都现成。它在 `dragover` 时读不到 `dataTransfer` 的内容，所以「拖的是谁」放在一个 signal 上，`dataTransfer` 只写一份占位 |
| 分屏另加一枚 `Split Editor` 按钮 | 动作区已有至多三枚按钮，再加一枚只为一个拖一下就能做的动作。键盘那半条由 `⌘\` / `Ctrl+\` 补上，不占动作区 |
| 分屏只留拖动、不给键盘入口 | HTML5 drag and drop 对键盘完全不可达，只用键盘的人打不开第二组；两组之间那把把手特意做成键盘可达，却要先用鼠标拖出来才用得上。一条快捷键的代价是全局快捷键从两条变三条，状态操作全是现成的 |
| `Split Editor` 快捷键做成移动（同拖动） | 只有一个 tab 时移走即源组空、合并回去，按了等于没按，而键盘用户最常见的起点（只开着一个文件）恰恰分不出来；VS Code 的 `splitEditor` 同样是复制。同一个 tab 两组各开一份本来就成立 |
| 已有两组时 `Split Editor` 什么都不做（或分出第三组） | 第三组违反封顶两组；什么都不做时键盘用户没有任何办法把一个 tab 送到另一组。开在另一组即可（VS Code 在这里会再分一组，封顶两组时退化成另一组）|
| 同一个 tab 在两组里各记各的上下文档 | 缓存按路径（commit 按 tab 键）存、不分组，两组各持一档时每次重取都按自己那档改写同一格，另一组的折叠行在 `Loading…` 与展开之间来回跳。上下文档本来就是「这份补丁要多少上下文」，按键一份即可 |
| 拖到另一组后保留预览态 | 拖动是明确的「我要在那边看它」，留成预览会被那一组下一次单击静默顶掉。VS Code 同样把拖过去的编辑器固定 |
